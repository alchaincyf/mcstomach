# 订单 → 规则｜归一、证据分级、置信度、矛盾追问

> 配套：`scripts/mcstomach.py normalize`（归一+计数）、`distill`（规则生成）。
> 脚本负责**算得准**，本文件负责**判断得对**。

---

## 1. 归一口径（确定性）

### 1.1 有效性判定

| `orderStatus` | 处理 | 权重 |
|---|---|---|
| `订单已完成` | 计入有效 | 1.0 |
| `订单已取消` | **剔除**，只进 `excluded_canceled` 计数 | 0 |
| 其他/未知字面值 | 保留，标 `status_unconfirmed` | **0.5**，并进 D 核对点 |
| 字段缺失 | 同上 | 0.5 |

**未知状态不剔除**：文档未穷举状态值，静默丢数据比降权+提示更糟。

### 1.2 套餐拆分：内含 ≠ 独立加点，必须分开记

同一份薯条：
- 在 `comboItemList` 里 → **combo_included**，权重 **0.5**（可能是套餐默认配的，不一定是主动选）
- 作为 `orderProductList` 顶层项 → **standalone**，权重 **1.0**（明确主动加点）

**两者不合并、不折算。** 陈述时分开说：
> 「薯条在 7 笔里都出现，其中 5 笔是**你单独加点的**。」

这比「你点了 6 次薯条」精确得多，也更难被用户反驳。

### 1.3 计数口径

- **出现笔数**（多少笔订单里有）= 判断「常点」的主口径
- **总份数**（quantity 累加）= 仅用于识别异常大单

⚠️ **份数含义不明时保留不确定。** `quantity` 在套餐 entry 与 combo 子项上的语义可能不同（是「几份套餐」还是「几件单品」文档未穷举）。所以：
- 顶层项 `quantity` → 直接累加，可用
- combo 子项 `quantity` → 只用于「出现过」，**不参与总额推断**，并在输出里标 `quantity_semantics: "unclear"`
- 任何基于份数的结论必须带「份数字段含义未完全确认」的标注，**不得**用它推断人数、食量、消费水平

### 1.4 团体单/代点识别（启发式，不得当结论）

命中**任一**：单 sku `quantity ≥ 3`｜整单品类数 ≥ 5｜整单总份数 ≥ 6｜同一 `productCode` 作为多个顶层 entry 重复出现。
→ 标 `group_suspected = true`，**权重降 0.3，且不进「可归于本人」计数**，进 D 核对点。

⚠️ **会误判。** 所以是「降权 + 追问」，不是「剔除」。用户确认是本人吃的，就升回正常权重。

`personal_valid_orders` = 非取消 **且** 非待确认团体单 的订单数。**C 段的 3 笔门槛用的是这个数。**

### 1.5 时段归类

由 `createTime` 小时得粗窗口：**早餐 05:00–10:30｜正餐 10:30–21:00｜夜间 21:00–次日 05:00**。

**禁止**从时段推断作息、职业、加班。「你经常深夜点单」只有在**用户自述**后才可写，并标注为用户自述。

## 1.6 v2 增补：订单级结构、分类明细、facts 层、来源状态

### 1.6.1 订单级套餐结构（四类**互斥**）

**按订单算，不按子项份数算。** 每笔个人有效单只落进一类：

| 值 | 含义 |
|---|---|
| `combo_only` | 只有套餐父项 |
| `standalone_only` | 只有独立单点 |
| `mixed` | 两样都有 |
| `unknown` | 判不出来（缺字段/结构异常） |

⚠️ **酱料、加料不算套餐。** 「麦乐鸡配蘸酱」不会因为出现「酱」就变成套餐；`番茄酱`/`沙拉酱`/`糖包`/`奶精`/`调味料` 归 **`condiment`**，既不参与主食多样性，也不构成套餐。
识别规则：命中 `酱/蘸/料包/调味/沾料/糖包/奶精/番茄沙司` 且**不含食物词**时才算调味；`酱香鸡腿堡` 这类含食物词的是正常餐品。
`is_combo_name()` 对 condiment 一律返回 `False`。

### 1.6.2 饮料属性分开记，别糊成一团

`drink_attrs(name)` 返回两个**互相独立**的属性，统计时**不合并**：

| 属性 | 取值 |
|---|---|
| `temperature` | `iced`（冰/冷）｜`hot`（热/暖）｜`unknown` |
| `sugar` | `zero_sugar`（无糖/零度/健怡/0糖/无热量）｜`unknown` |

「冰美式」与「热美式」是**两个**计数项；带「无糖/零度/健怡」标记的饮料与不带标记的，也是**两个**计数项。讲偏好时保留区别，别压缩成「你爱喝某种饮料」。

### 1.6.3 facts 层：时间与金额

**时间**

- 解析 → `date_state: parsed`，同时给 `date_moment`（落盘前转 ISO，datetime 不可直接序列化）；
- 解析不了 → `unparsed`；未来时间 → `invalid`。**两种都不冒充正常**，不参与频率推断。
- 给出 `as_of`、`window_span_days`（可见窗口跨度）、相邻单间隔、`days_since_last_visible`（距最近一次**可见**下单天数）。
- `recency_state == "stale"`（> `STALE_AFTER_DAYS` = 90 天）→ 输出旧档案＋邀请更新，**不**宣称「你已经不吃了」。
- **最近 10 笔限制必须写在输出里**：这是 `order-list` 的上限，不是全量。

**金额**

- **只算已确认的个人有效单**（`personal_valid_orders`）。共享单**单独整单列出**，不摊到人头。
- **单位未核实 → 不给任何数值**：`total`/`mean`/`median`/`min`/`max`/`range` 全为 `null`，`stability` 为 `unknown`。不许猜「元」还是「分」。
- `realTotalAmount`（历史单）与 `calculatePrice`（疑似**分**）**不许混用**；后者单独隔离，不参与任何金额推断。
- **真的无量纲**：稳定性用**变异系数**（`CV_STABLE_MAX = 0.15`），`dispersion.dimensionless` 必须为 `true`。**不许**用 `max-min ≤ 10` 这种带单位的差值冒充。
- **不许**把「金额排得整齐」推成「这个人有预算纪律」。

### 1.6.4 来源状态

见 `portfolio-schema.md` §1.1。要点：

- 分不清「没接上 / 接口失败 / 账号真空 / 无有效样本 / 仅 1 单 / 久未下单 / 常规」时，**先分类再说话**；
- `fetch_failed` 与 `empty_account` **绝不能混**——接口失败时说「账号没记录」是错的；
- 全部未确认 / 全部取消 / 全部共享未确认 → `no_valid_samples`，**不生成稳定类型**。

### 1.6.5 新品证据单独留口

只有**有可靠上市日期或明确新品标记、且对得上订单日期**时才讲「爱尝新」；
否则只讲**可见样本内的变化与回购**（例如 `novelty.claimable == false` 时不许下尝新结论）。

## 2. 证据分级

```json
{ "type": "order_stat",
  "stat": "某一配餐在 7 笔可归于本人的有效订单中出现 7 次，其中 5 次为独立加点",
  "sample": "7 笔",
  "strength": "high",
  "source": "order-list" }
```

| strength | 条件 |
|---|---|
| `high` | ≥3 笔本人有效订单，且含独立加点或多维度一致 |
| `medium` | ≥3 笔但有降级因素（全部套餐内含／含未确认状态） |
| `low` | 1~2 笔，或高度依赖团体单 |
| `user_stated` | 用户自述（`source.kind = questionnaire`），**标注为自述，不当订单证据** |

## 3. 置信度 → 能否直接给

| 置信度 | 处理 |
|---|---|
| high | 直接给，**标依据**；`confirmed_by: null` 待用户点头 |
| medium | 给，标「倾向」，并作为 D 核对点候选 |
| low | 给，必须写明「样本不足，可能不准」 |
| 矛盾项 | **先问再写**，不落规则 → 进 `unresolved[]` |

---

## 4. 矛盾处理：问最有区分度的一句

| 矛盾 | 信号 | 问法（挑一句） |
|---|---|---|
| 代点 vs 本人 | 团体假设命中 | 「X 月那笔点了 4 份【A】，你自己吃还是帮人带的？」 |
| 默认 vs 主动 | 某组合永远是默认形态、从无替换 | 「这套餐是按默认配的，还是里面有哪样你特意换过？」 |
| 同一品类忽有忽无 | 近几笔有、更早几笔完全没有 | 多半是新品上市，**不用问**，标注时间范围即可 |
| 口味冲突 | 自述「不吃辣」但订单有辣味品 | 「你提到不吃辣，但订单里有【辣味品】——是给别人点的，还是这条要改？」 |

**追问规则**：一轮最多 2 题；总计最多 5 题；**答过的不重复问**（记 `asked_question_ids`）；能用别的证据绕开就先绕开。

## 5. 维度字典

| dimension | 含义 | 示例 |
|---|---|---|
| `staple` | 主食 | 偏好板烧类堡 |
| `side` | 配餐 | 薯条几乎必点 |
| `drink` | 饮品 | 常点某种饮品（**保留冰/热、无糖/含糖，不合并**） |
| `breakfast` | 早餐时段/品类 | 常在早餐窗口点单 |
| `hard_avoid` | **硬忌口**，推荐前必过滤 | 不吃辛辣 |
| `must_have` | 不可妥协的一口 | 一顿里必须有薯条 |
| `session` | 场景/方式 | 偏好外送 |
| `budget` | 价格取舍 | 倾向某区间 |
| `novelty` | 尝新 vs 稳妥 | 愿意试新品 |

`kind` ∈ `hard_avoid` / `preference` / `constraint` / `habit`。
**`hard_avoid` 优先级最高**：推荐时先过滤，过滤到没得选就如实说没得选。

```
raw_orders:                10
excluded_canceled:         2
status_unconfirmed:        1     (降权 0.5，仍计入有效)
valid_orders:              8     (10 - 2 取消)
```

- `unresolved`｜「有一笔点了 4 份【麦辣鸡腿堡】，是你自己吃的吗？」（团体假设，`dimension: session`）
